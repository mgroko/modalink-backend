# Ficha técnica — Colaboraciones automáticas en publicaciones históricas

> **Estado:** propuesta de diseño. Pendiente de implementación.
> **Relación:** extensión administrativa de
> `docs/frontend/ficha-tecnica-colaboraciones-automaticas.md`.
> **Objetivo:** procesar publicaciones e imágenes ya existentes para detectar
> coincidencias y generar propuestas, sin depender de una nueva subida.

## 1. Problema

La detección automática se dispara al crear una publicación o al agregar
imágenes nuevas. Las publicaciones creadas antes de la funcionalidad, o cuyas
imágenes no tienen `phash`, nunca fueron analizadas.

Se necesita un proceso administrativo que:

- calcule las huellas faltantes (`sha256_contenido`, `phash`);
- ejecute el mismo pipeline de verificación sobre publicaciones históricas;
- genere propuestas pendientes;
- sea idempotente, observable y no afecte la latencia de subida.

## 2. Alcance

Incluye:

- publicaciones `ACTIVA` de perfiles `ACTIVO` y usuarios `ACTIVO`;
- imágenes vinculadas a publicaciones (`imagen_publicacion`);
- backfill de huellas faltantes;
- detección con SHA-256, pHash, ORB y multi-recorte;
- ejecución manual desde el panel administrador.

No incluye:

- confirmar o rechazar propuestas automáticamente;
- recalcular huellas que ya existen;
- modificar el algoritmo o los umbrales de detección;
- procesar imágenes de perfil, moodboard o polaroids;
- una interfaz de usuario (se detalla en una ficha aparte).

## 3. Modos de procesamiento

| Modo | Qué hace |
|---|---|
| `HUELLAS` | Solo calcula `sha256_contenido` y `phash` faltantes |
| `DETECCION` | Solo detecta coincidencias; omite imágenes sin pHash |
| `AMBOS` | Primero completa huellas y después detecta (recomendado) |

## 4. Endpoints

Todos bajo `/admin/colaboraciones-automaticas/historicas` y restringidos a
administradores.

`GET /admin/colaboraciones-automaticas/historicas` devuelve los jobs paginados

### 4.4 Errores del job

`GET /admin/colaboraciones-automaticas/historicas/{id}/errores` devuelve, de
forma paginada:

```json

  "idImagen": 87,
```

### 4.5 Cancelar

`POST /admin/colaboraciones-automaticas/historicas/{id}/cancelar` marca el job
como `CANCELADO`. El worker lo detecta entre lotes y se detiene sin borrar lo
ya procesado.

## 5. Modelo de datos

### 5.1 Job

```sql
CREATE TABLE procesamiento_colaboracion_historica (
    id_procesamiento          int8 GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    estado                    varchar(30)  NOT NULL,
    modo                      varchar(20)  NOT NULL,
    filtro_id_publicacion     int8,
    filtro_id_perfil          int8,
    filtro_fecha_desde        timestamp,
    filtro_fecha_hasta        timestamp,
    notificar                 boolean      NOT NULL DEFAULT false,
    tamano_lote               int4         NOT NULL DEFAULT 50,
    limite_publicaciones      int4,
    total_publicaciones       int4         NOT NULL DEFAULT 0,
    publicaciones_procesadas  int4         NOT NULL DEFAULT 0,
    total_imagenes            int4         NOT NULL DEFAULT 0,
    imagenes_procesadas       int4         NOT NULL DEFAULT 0,
    hashes_calculados         int4         NOT NULL DEFAULT 0,
    propuestas_creadas        int4         NOT NULL DEFAULT 0,
    propuestas_omitidas       int4         NOT NULL DEFAULT 0,
    errores                   int4         NOT NULL DEFAULT 0,
    ultimo_id_publicacion     int8,
    id_usuario_admin          int8         NOT NULL,
    fecha_inicio              timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    fecha_fin                 timestamp,
    mensaje_error             varchar(1000),
    CONSTRAINT "PK_procesamiento_colaboracion_historica"
        PRIMARY KEY (id_procesamiento)
);

CREATE INDEX idx_proc_colab_hist_estado
    ON procesamiento_colaboracion_historica(estado);

CREATE INDEX idx_proc_colab_hist_fecha
    ON procesamiento_colaboracion_historica(fecha_inicio DESC);
```

### 5.2 Errores

```sql
CREATE TABLE procesamiento_colaboracion_historica_error (
    id_error             int8 GENERATED BY DEFAULT AS IDENTITY NOT NULL,
    id_procesamiento     int8         NOT NULL,
    id_publicacion       int8,
    id_imagen            int8,
    nombre_archivo       varchar(255),
    mensaje              varchar(1000) NOT NULL,
    fecha_registro       timestamp    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "PK_proc_colab_hist_error" PRIMARY KEY (id_error),
    CONSTRAINT "FK_proc_colab_hist_error_job"
        FOREIGN KEY (id_procesamiento)
        REFERENCES procesamiento_colaboracion_historica(id_procesamiento)
        ON DELETE CASCADE
);

CREATE INDEX idx_proc_colab_hist_error_job
    ON procesamiento_colaboracion_historica_error(id_procesamiento);
```

### 5.3 Estados

| Estado | Descripción |
|---|---|
| `PENDIENTE` | Job creado, esperando worker |
| `EN_PROGRESO` | Procesando lotes |
| `COMPLETADO` | Terminó sin errores |
| `COMPLETADO_CON_ERRORES` | Terminó con errores parciales |
| `CANCELADO` | Cancelado por el administrador |
| `FALLIDO` | Error fatal del job |
| `INTERRUMPIDO` | El servidor se reinició con el job en curso |

## 6. Flujo de procesamiento

1. El administrador previsualiza el impacto.
2. Al procesar, se valida que no haya otro job `EN_PROGRESO`.
3. Se crea el job en `PENDIENTE` y se responde `202`.
4. Un worker dedicado lo toma y lo pasa a `EN_PROGRESO`.
5. Itera publicaciones con paginación por clave (`id_publicacion > ultimo_id`)
   y filtros, en lotes de `tamano_lote`.
6. Por cada publicación, en una transacción corta:
   - carga sus imágenes;
   - para cada imagen, completa `sha256_contenido` y `phash` si faltan;
   - ejecuta la detección con el mismo pipeline de la subida;
   - actualiza contadores y `ultimo_id_publicacion`.
7. Entre lotes verifica si el job fue cancelado.
8. Al terminar, marca `COMPLETADO` o `COMPLETADO_CON_ERRORES`.
9. Registra la auditoría.

### 6.1 Reutilización del detector

Se extrae del flujo actual una operación reutilizable, por ejemplo:

```java
DeteccionResultado detectarImagen(
        Publicacion publicacion,
        Imagen imagen,
        boolean notificar);
```

Tanto la subida como el proceso histórico la usan. El proceso histórico no debe
depender de `imagenesNuevas` ni del request.

### 6.2 Backfill de huellas

- `sha256_contenido`: SHA-256 de los bytes del archivo almacenado.
- `phash`: `HuellaImagenService.phash(bytes)`.
- `phash_version`: `HuellaImagenService.PHASH_VERSION`.
- Si el archivo no existe o no se puede decodificar, se registra el error y se
  omite la imagen; el job continúa.

## 7. Idempotencia y concurrencia

- El índice único de propuestas pendientes y `existsByParYEstados` evitan
  duplicados si el job se ejecuta dos veces.
- Un par de publicaciones puede evaluarse en ambos sentidos; la segunda
  evaluación se cuenta como `propuestasOmitidas`.
- Solo puede haber un job `EN_PROGRESO` a la vez. Un segundo intento responde
  `409`.
- Si el servidor se reinicia, los jobs `EN_PROGRESO` se marcan
  `INTERRUMPIDO` al arrancar. El administrador puede relanzar el proceso; la
  idempotencia evita duplicados.

## 8. Notificaciones

Por defecto `notificar=false` para no generar una avalancha de notificaciones
históricas. Las propuestas igual aparecen en el listado de pendientes de cada
perfil.

Si `notificar=true`, se envían las notificaciones normales de detección, con un
límite configurable por job para evitar spam. Esta decisión queda abierta.

## 9. Seguridad y auditoría

- `@PreAuthorize("hasRole('ADMINISTRADOR')")` en el controlador.
- `@AuditarOperacion` en el servicio que crea y ejecuta el job.
- Evento de auditoría:
  - entidad: `PROCESAMIENTO_COLABORACION_HISTORICA`;
  - evento: `EJECUTADO`;
  - detalle: modo, filtros, contadores y estado final.
- Los errores por imagen no se consideran eventos de auditoría; se guardan en
  la tabla de errores del job.

## 10. Rendimiento

- Paginación por clave, sin `OFFSET` profundo.
- Una transacción por publicación, no una transacción global.
- Worker dedicado de un solo hilo para no competir con la detección de subidas.
- Lote configurable (por defecto 50 publicaciones).
- La consulta de candidatos por pHash recorre la tabla de imágenes; para
  volúmenes grandes conviene evaluar bucketing o un índice funcional.
- Estimación: 5–10 imágenes/s por worker (decodificación + ORB + RANSAC), por
  lo que 1.000 imágenes tardan aproximadamente 2–3 minutos.

## 11. Errores HTTP

| HTTP | Caso |
|---|---|
| `400` | Filtros inválidos (rango de fechas invertido, lote fuera de rango) |
| `403` | El usuario no es administrador |
| `404` | Job inexistente |
| `409` | Ya hay un job `EN_PROGRESO` o el job no se puede cancelar |
| `422` | No hay publicaciones que cumplan los filtros |

## 12. Tests

### Unitarios

- Construcción de filtros y paginación por clave.
- Backfill de `sha256_contenido` y `phash`.
- Idempotencia: dos ejecuciones no duplican propuestas.
- Modo `HUELLAS` no crea propuestas.
- Cancelación entre lotes.
- Job con errores parciales termina en `COMPLETADO_CON_ERRORES`.

### Integración

- Publicaciones históricas sin pHash: el job completa huellas y crea
  propuestas.
- Segunda ejecución: `propuestasCreadas = 0`, `propuestasOmitidas > 0`.
- Imagen con archivo faltante: se registra el error y el job continúa.
- Dos jobs simultáneos: el segundo responde `409`.
- Seguridad: usuario no administrador recibe `403`.
- Auditoría registrada.
- Reinicio con job en curso: pasa a `INTERRUMPIDO`.

### Rendimiento

- Procesar un lote de N imágenes dentro de un tiempo aceptable y sin bloquear
  la subida.

## 13. Criterios de aceptación

- El administrador puede previsualizar el impacto antes de ejecutar.
- El job completa huellas faltantes y genera propuestas solo para
  coincidencias verificadas.
- Reejecutar el proceso no duplica propuestas.
- El progreso y los errores son consultables.
- Un fallo por imagen no aborta el job.
- El proceso no afecta la latencia de subida (worker dedicado).
- La acción queda auditada.
- Solo accesible para administradores.

## 14. Fuera de alcance

- Interfaz de usuario del panel administrador.
- Ejecución automática por scheduler.
- Recalcular huellas existentes.
- Confirmación o rechazo masivo de propuestas.
- Cambios en los umbrales de detección.

## 15. Decisiones pendientes

1. ¿`notificar` debe ser `false` por defecto? (recomendado: sí).
2. ¿Se necesita reanudación exacta tras un reinicio o alcanza con relanzar?
3. ¿Los errores por imagen van a tabla propia o alcanza con contadores y logs?
4. ¿Se incluyen publicaciones `OCULTA`? (recomendado: no, igual que la
   detección normal).
5. ¿Hace falta una fecha de corte por defecto o el administrador siempre elige
   el rango?
